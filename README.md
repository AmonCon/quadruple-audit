# quadruple-audit

[![Version](https://img.shields.io/badge/version-1.2.1-blue)](https://github.com/AmonCon/quadruple-audit/releases) [![License: MIT](https://img.shields.io/badge/license-MIT-green.svg)](LICENSE)

四轮审查：一套面向 AI 编程智能体的审查流程，目标是让每个结论**都能被独立复核**，并且让「查了什么」「没查什么」在输出里分得开。

> **成本警告：这不是一个便宜的流程。** 一次完整审查要派出几十个子智能体（样例那次是 9 个视角单元 + 21 个复现者 + 空白猎手 + 裁决者），实测约 **6000 万 token**。审一个文件的代价远低于这个数，但审一个完整功能，消耗可达单轮审查的几十到上百倍（取决于分区数与发现数量）。预算有限或只想先试水，先看「成本」一节的**轻量模式**。**完整流程用不用，读「什么时候不该用」一节的最后一段再决定。**

## 它解决什么问题

模型审查自己刚写完的代码，会漏掉自己的错误。原因不是不努力，而是上下文：它得出「这里没问题」之后，这个判断已经留在上下文里，再让它「重新检查」，它会顺着原有思路找理由。

一个具体例子：让模型检查自己算的 `11 × 11 = 121`，连查五遍，五遍都说对——因为它在第二轮已经看过「121」这个答案，回不到不知道的状态。

所以本流程的每一层取证都由**没看过上一层答案的读者**完成：

- 复现者只拿到 `where / what / evidence` 三个字段，拿不到提出者的推理过程。
- 它必须自己打开文件、自己跑查询、自己看命令输出。
- 它的结论可以推翻提出者。

## 四个阶段

四个编号阶段，外加两个按需触发的环节——前置的「锚定」（确认要审的是不是用户真正关心的问题），和候选多于 3 条时的「归类」（见表后说明）。

| 阶段 | 谁在做 | 拿到什么 | 产出 |
|------|--------|----------|------|
| 零 · 锚定 | 需求锚定者 | 用户原话 | 该审什么、铁律是什么、切哪些分区、风险多高 |
| 一 · 取证 | 视角 × 分区的二维扇出 | 各自那一小块 | 带证据的候选发现 |
| 归类（按需） | 同根因归类者 | 全部候选的 where + what | 同源分组 |
| 二 · 复现 | 每条发现一个复现者 | 只有 where/what/evidence | 复现 / 否定 / 存疑 |
| 三 · 反查 | 空白猎手 + 翻案者 | 覆盖清单 / 被否定项 | 遗漏项与翻案项 |
| 四 · 裁决 | 裁决者 | 前几个阶段的结构化结果 | 收敛清单 + 系统性缺陷 + 覆盖账本 |

「归类」只在候选超过 3 条时触发，用来避免多个视角报同一根因时付多份复现费。

报告里还有一层「系统性缺陷」：条目按「一次动手能修完」为单位（方便分工），但同一类毛病散落在多个模块时会单独标出来（例如十条里四条都是「写操作不检查结果」）。两个视角都要有，缺哪个都会误判。

## 为什么是四轮

这个数字来自实测，不是设计出来的。

最初的问题很简单：让模型复查自己刚写的代码，一轮经常不准；再查一遍、再查一遍，第二轮、第三轮仍会出错——它看得见自己前面的结论，就回不到「不知道」的状态，倾向于顺着原思路找理由。反复试下来，到第四轮、用前面没用过的角度把前三轮的结果都过一遍之后，结论才基本稳定。

把这段经验拆开，得到两条比「四」更重要的东西：

1. **问题出在上下文污染，不在轮次数量。** 复查者看得见上一轮的答案，单纯加轮次是在赌运气。
2. **让第四轮稳下来的，是「新角度」而不是「又一遍」。**

所以现在的四轮不是「把同一件事再审四遍」，而是四种不同的操作：取证、证伪、覆盖审计、收敛。每一轮由没看过上一轮答案的读者完成；第四轮（裁决）不回顾前三轮的思考过程——那会让证据在转述里蒸发——只处理它们的结构化结果。

「四」是起点，不是信仰：哪个阶段产生不了新信息，就合并或删掉它。实测收敛是当时的经验观察，不是保证——本流程保证的是每个结论可独立复核，不是「绝不出错」。

## 为什么不是「N 个视角并行」就够了

阶段一的所有视角，无论 N 多大，做的都是同一件事：读东西、产出主张。它们是**生产者**。

后面三轮做的是另外三类操作：**证伪**（拿结论回源头重推，且看不到提出者的推理）、**覆盖面审计**（只问哪块没人看过）、**收敛**（去重、统一标尺、跑命令）。

加视角能提高召回，换不来证伪。所以这里的 N 只由证据通道数量决定（通常 2–5），真正的并行度来自**分区扇出**——把工作切成独立单元，每块派一个人读透。

「复现 ≠ 视角」这一点有实测支持：一次真实审查里，三个复现者全部修正了提出者的因果链。分区扇出的收益（每块被细读而非 skim）尚未单独测量。

三个设计要点：

1. **视角按证据通道分化。** 读代码、查数据库、跑命令——如果几个视角只是措辞不同、看的都是同一份文本，那是几份相关误差，会一起漏掉同一块。其中「状态与并发」是按需视角（`risk: high` 且目标有状态交织时启用）：提取状态机、拿铁律逐条去撞、用脚本做组合穷举，把「想用例」换成「枚举状态」。
2. **否定必须被攻击一次才能进「已排除」。** 把真实问题判成不存在的代价，远高于误报。
3. **确定性检查由退出码决定。** `npm test` 的退出码是事实，「子智能体说测试通过了」不是。

## 安装

一行安装——任何机器、任何 agent，不需要先 clone 仓库。macOS / Linux / Git Bash（先下载脚本再运行，不盲管道执行）：

```bash
curl -fsSL https://github.com/AmonCon/quadruple-audit/raw/main/install.sh -o install-qa.sh && bash install-qa.sh && rm install-qa.sh
```

Windows PowerShell：

```powershell
irm https://github.com/AmonCon/quadruple-audit/raw/main/install.ps1 | iex
```

脚本会自动探测本机的 agent 技能目录（Claude Code、ZCode、通用 `~/.agents/skills` 等），拉取最新文件装进去，并打印装到的**版本号和路径**。要指定目录，先设环境变量 `QUADRUPLE_AUDIT_SKILLS_DIR` 再运行。

网络环境拿不到 GitHub raw 内容时，退回克隆安装：`git clone` 本仓库后运行 `./install.sh`（Windows：`powershell -ExecutionPolicy Bypass -File install.ps1`）。也可以手动放到任意一个技能目录：

| 宿主 | 路径 |
|------|------|
| Claude Code（全局） | `~/.claude/skills/quadruple-audit/` |
| ZCode / 多数 agent（全局） | `~/.agents/skills/quadruple-audit/` |
| 项目级（任何 agent） | `<repo>/.claude/skills/quadruple-audit/` |

更新：重跑一遍上面同样的命令即可（克隆安装的则 `git pull` 后重跑脚本）；卸载：删掉技能目录。

## 通用性

这个技能不绑定任何东西：不需要 npm 包、不需要构建步骤、不需要第三方服务、不需要 API 密钥，也不挑宿主。任何能读文件、能派子智能体的 agent（Claude Code、ZCode、Cursor、Codex、自建工具……），在任何操作系统、任何项目、任何机器上都能跑。

**审查是只读的。** 审出问题不等于被授权修复：不修改被审查的文件、不跑迁移、不写库、不建单不扣库存、不部署不提交。需要查库时只用 `SELECT`、串行、带 `LIMIT`，密钥不进报告和账本。想验证并发与写入路径，用状态机枚举，而不是真的写进去——这条边界写在 `SKILL.md` 的「适用范围与权限边界」和「查库纪律」两节。

安装只影响「你的 agent 多了一个技能」，不影响被审查的项目：审查者在运行时自己读文件、自己跑命令，项目的凭据不经过技能本体（见 `SKILL.md` 的「数据源探测」一节）。

## 使用

**用法一 · 直接检查。** 把一个功能、一个模块或一个问题交给它，从零取证跑完整流程：

```
/quadruple-audit 检查社区帖子的收藏功能是否正常
```

**用法二 · 复核已有的结论。** 另一个审查者（人或 AI Agent）给出了具体发现时，把它的 `where / what / evidence` 原样交给本流程，让结论回源头重推一遍：

```
/quadruple-audit 复核这条结论是否属实：
where: services/favorite/index.ts:115
what: 已收藏时点击 → 23505 → 卡在未收藏
evidence: <你亲眼看到的行内容 / SQL 与返回 / 命令与退出码>
```

两种用法走的是同一套流程，区别只在锚定阶段要回答的问题：一个是「这里到底有没有问题」，一个是「这条结论成不成立」。复现者只拿到 `where / what / evidence`，拿不到提出者的推理，它可以复现、可以否定、可以存疑——所以被复核的结论不成立时，它会说出来，而不是顺着补理由。

想先验证它好不好使？拿 [`examples/fixture/`](examples/fixture/) 跑一次冒烟测试：一个零依赖的迷你项目，埋了 3 个真问题和 1 个应被否掉的假问题，期望产出见 [`examples/fixture-expected.md`](examples/fixture-expected.md)。

## 两种运行方式

流程与宿主无关，调度方式按能力分两档：

- **B 档 · 有子智能体（默认，推荐）**：`SKILL.md` 里给了可直接抄的派发提示词骨架。几乎所有 agent 环境都能用，本流程的两次真实审查都是这样跑完的。
- **C 档 · 只有自己**：降级为纪律约束（每轮重新取证、换阅读顺序、分文件写），见 `SKILL.md` 的「C 档」一节。

B 档的结构性隔离靠提示词实现：复现者拿到的只有 `where` / `what` / `evidence` 三个字段，看不到提出者的推理过程。

## 它实际审出了什么

三条发现来自两次真实审查（同一个中型 React + Supabase 项目的收藏功能，均已脱敏）。第一条出自本仓库附带的完整样例报告（[`examples/sample-report.md`](examples/sample-report.md)）；第二、三条出自另一次审查，其完整报告未随仓库发布。三条分别说明这套流程的三个不同作用：

**一、抓到一处持久性数据错误。** 同一批计数触发器在历史上有两份同时生效，每次收藏被加了两次；后来只删掉了多余那个，**从没回填过**。也就是说详情页显示的收藏数接近真实值两倍，而且不会自愈。

**二、把夸大降了级。** 提出者报「软件收藏计数不更新，medium」。复现者回源头查完，发现那个字段**在整个仓库里没有任何组件渲染**，从不展示也不排序，于是降到 low。同时它补充：同类的 rating 计数器有完全相同的缺失。

**三、否掉了一个编造的崩溃。** 一条发现说「外键错误未处理会白屏」。复现者打开代码发现 `throw` 就在同一个 `try` 块里，下面紧跟 `catch`，链路根本不逃逸。翻案复核员不服，**真的跑了那段代码**（注入真实的 23503 错误，四条路径全返回普通对象、无一逃逸），然后把原判维持为「不成立」，同时指出真问题是个更轻的：数据库原文会直接显示给用户。

第三条最能说明为什么要有第二阶段：**没有它，这条编造的崩溃会直接进报告。**

## 成本

比单轮审查贵得多，实测数字：

| 场景 | 消耗 |
|---|---|
| 完整四轮（3 视角、无分区、34 条候选） | 约 5300 万 token |
| 完整四轮（3 视角 × 3 分区、51 条候选） | 约 6000 万 token |
| 单视角，加「先定位再读」约束后 | 从 960 万降到 550 万（-43%） |
| 轻量模式（锚定 + 单视角 + 仅复现 high/medium） | 数百万 token，约为完整四轮的 1/10 |

控制手段：限制读取范围（最大项）、控制分区数量、同根因归类、复现分级、单次复现条数上限。

### 轻量模式

如果完整四轮超出预算，或者第一次用、想先看看输出质量：锚定 + 单个视角取证 + 只对 high/medium 发现派复现，数百万 token 就能出一份带覆盖账本的小报告。它不做扇出和反查，覆盖有限——这一点必须写进账本，不能装作跑过完整流程。结论可疑、或代价确实高时，再升级完整四轮。

## 什么时候不该用

| 情况 | 用什么 |
|---|---|
| 改文案、调样式、单行修改 | 不用，直接改 |
| 目标明确、只有一条路径 | 一轮普通审查 |
| 已审过，只想复核某个具体点 | 派单个复现者，不要重跑四轮 |
| 第一次试用，想先看输出质量 | 轻量模式（见「成本」一节） |
| 支付、权限、数据删除、资金结算 | **用**，值得这个成本 |
| 首次接触陌生代码库 | 用，但先把分区切小 |

判断标准是**错了要付什么代价**。代价低的走轻量流程，并在覆盖账本说明跳过了什么。

## 已知局限

写清楚这些，比声称「更准」诚实。

- **不保证召回。** 视角只能覆盖它们想到的通道，想不到的仍然漏。
- **没有基准数据。** 本流程提高的是「结论可复核」和「覆盖可见」，不是已被证明的准确率提升。没有对照实验前不应这样宣称。
- **确定性检查只覆盖项目已有的检查。** 项目没写测试，第四阶段变不出测试。
- **状态机枚举验证的是抽象，不是代码。** 穷举只对提取出的状态机负责，反例必须回源复现；「枚举通过」不能写成「并发已验证无问题」。
- **降级到 C 档时对抗性显著削弱。**

## 贡献

最有价值的贡献是**反例**：一个本该被审出来、但没审出来的案例，连同当时的输入。比改进提示词措辞有价值得多。反例和误报直接开 issue——仓库备了两个模板（missed-case / false-positive）。

修改流程时请守住三条，它们是这套方法成立的前提：

1. 复现者拿不到提出者的推理。
2. 被否定的发现要经过一次专门攻击。
3. 输出里必须区分「查了没问题」和「没查」。
